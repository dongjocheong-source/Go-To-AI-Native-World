결제 정보는 무조건 안전하게, 로그는 1초에 10만 개씩, 오타를 쳐도 검색되게 — 이 질문들의 답은 서로 다른 DB여야 합니다. 5가지 DB 유형만 확실히 알아두면 시스템 아키텍처를 보는 눈이 트입니다.

RDB vs NoSQL Redis 상황별 선택 가이드
1. Relational DB

RDB (관계형 DB)

행(Row)과 열(Column)로 이루어진 '엑셀 표'와 같습니다. 50년 넘게 IT 생태계를 지배해 온 근본입니다.

PostgreSQL ⭐현업 최애MySQL / MariaDBOracle (엔터프라이즈)

👍 장점

01
데이터 무결성 (ACID)트랜잭션이 보장되어 "돈은 보냈는데 상대는 못 받는" 사고가 없습니다.
02
정규화 & JOIN중복을 없애고 여러 테이블의 복잡한 관계를 표현하기 좋습니다.

👎 단점

01
유연성 부족스키마가 엄격해 컬럼 하나 추가에도 마이그레이션이 필요합니다.
02
스케일링 어려움Scale-up은 쉽지만, 여러 대로 나누는 샤딩은 복잡합니다.
schema.sql
-- 스키마를 미리 엄격하게 정의
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE
);

-- JOIN으로 관계 조회
SELECT u.username, o.product_name
FROM users u JOIN orders o ON u.id = o.user_id;
추천 용도 — 회원 정보, 결제 시스템, 주문 내역, 재고 관리처럼 정확성이 생명인 곳
2. NoSQL (Document)

NoSQL — 유연성과 확장성을 택하다

RDB의 엄격함 대신 유연성과 확장성을 택한 DB. 그중 Document DB가 가장 대표적입니다.

MongoDBDynamoDB (AWS)

👍 장점

01
Schema-less구조가 자주 바뀌어도 그냥 넣으면 됩니다.
02
확장성처음부터 샤딩을 염두에 둔 설계로 대용량 처리에 유리합니다.

👎 단점

01
데이터 일관성RDB만큼 엄격한 트랜잭션을 지원하지 않는 경우가 많습니다(최종 일관성).
02
JOIN 어려움애플리케이션 레벨에서 데이터를 합쳐야 할 때가 많습니다.
MongoDB Query
// 스키마 없이 JSON을 그대로 저장
db.users.insertOne({
    username: "minji",
    skills: ["Python", "Docker"],   // 배열도 그대로
    meta: { level: 99, class: "S" }    // 중첩 객체도 가능
});

db.users.find({ "meta.level": { $gt: 50 } });
추천 용도 — 데이터 구조가 자주 바뀌는 스타트업 초기 모델, 로그 데이터, 콘텐츠 관리(CMS)
3. In-Memory DB

In-Memory DB — 속도가 곧 생명

디스크는 느립니다. In-Memory DB는 데이터를 초고속 RAM에 저장합니다.

Redis ⭐압도적 1위Memcached

👍 장점

01
미친 속도디스크 DB보다 수십~수백 배 빠릅니다 (마이크로초 단위 응답).

👎 단점

01
휘발성전원이 꺼지면 데이터가 사라집니다 (Redis는 디스크 저장 옵션이 있지만 주 용도는 아님).
02
용량 제한RAM 가격이 비싸 대용량 저장엔 부적합합니다.
redis_example.py
import redis
r = redis.Redis(host="localhost", port=6379)

# 캐싱 + 1시간 뒤 자동 삭제
r.set("user:1:profile", '{"name": "Minji"}', ex=3600)

# 실시간 랭킹 (Sorted Set)
r.zadd("game_ranking", {"userA": 100, "userB": 250})
top = r.zrange("game_ranking", -1, -1, withscores=True)
추천 용도 — 캐싱, 세션 스토어, 실시간 랭킹/카운터처럼 빠른 갱신이 필요한 데이터
4. Search Engine

Search Engine — 검색에 특화된 구조

RDB의 LIKE 검색은 데이터가 많아지면 느려지고 조사가 붙으면 검색이 안 됩니다. Search Engine은 '역색인(Inverted Index)' 구조로 텍스트 검색에 특화되어 있습니다.

Elasticsearch (ELK)OpenSearch

👍 장점

01
전문 검색(Full-text)형태소 분석으로 "먹기 좋은 사과"를 검색해도 "사과는 맛있다"를 찾습니다.
02
복합 검색위치 기반, 필터링, 점수 기반 랭킹 등 복잡한 검색이 빠릅니다.

👎 단점

01
실시간성 부족인덱싱에 시간이 걸립니다 (준실시간).
02
관리 비용클러스터 관리가 복잡하고 리소스를 많이 씁니다.
Elasticsearch Query
// "apple" 관련 + "pro"가 들어간 상품 (오타 허용)
GET /products/_search
{
  "query": { "bool": { "must": [
    { "match": { "name": "apple" } },
    { "fuzzy": { "model": "pro" } }
  ]}}
}
추천 용도 — 쇼핑몰 상품 검색, 블로그 검색, 로그 분석 및 모니터링(Kibana 연동)
5. Vector DB

Vector DB — AI 시대의 새 주인공

기존 DB는 '단어'가 일치해야 찾지만, Vector DB는 데이터의 '의미(벡터)'를 저장합니다.

Pinecone (SaaS)Milvus / ChromaPGVector

👍 장점

의미 기반 검색(Semantic Search)이 가능합니다. "배고파"를 검색하면 "맛집 리스트"를 찾아줍니다.

👎 단점

정확한 키워드 매칭(BM25)에는 오히려 약할 수 있습니다.

vector_search.py (개념)
# 1. 질문을 벡터로 변환
query_vector = model.encode("배고파")

# 2. 벡터 거리가 가장 가까운 문서 검색
results = vector_db.search(query_vector, top_k=3)
# → ["근처 맛집 리스트", "야식 추천 메뉴", ...]
추천 용도 — RAG(검색 증강 생성), 이미지/비디오 유사도 검색

Conclusion

마치며

개발자가 알아야 할 5가지 핵심 DB 유형을 정리했습니다.

01정석이 필요하면 RDB, 유연함이 필요하면 NoSQL, 속도가 생명이면 Redis, 검색이 중요하면 Elasticsearch, 의미를 찾아야 하면 Vector DB입니다.
02하나의 서비스도 보통 여러 DB를 함께 씁니다 — 회원정보는 RDB, 세션은 Redis, 검색은 Elasticsearch처럼 목적별로 조합하는 것이 현실적인 아키텍처입니다.
기억할 것 한 줄 — "DB 뭐 써야 해요?"의 정답은 하나가 아니라, 데이터의 성격에 달려 있습니다.
