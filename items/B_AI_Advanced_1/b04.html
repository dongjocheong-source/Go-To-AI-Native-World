루프 엔지니어링
(Loop Engineering)이란 무엇인가

"저는 더 이상 AI에게 프롬프트를 치지 않습니다. 제 일은 AI가 스스로 일감을 찾고 수정하게 만드는 '루프(Loop)'를 짜는 것입니다." — 구글 엔지니어링 디렉터 Addy Osmani. 사람이 매번 프롬프트를 입력하던 역할을 AI 자동화 시스템으로 대체하는 방법론, 그 5대 구성요소와 Claude Code 실전 구축까지 정리합니다.

5대 핵심 부품 + 메모리 L1→L2→L3 점진적 도입 프롬프트 vs 루프
Overview

루프 엔지니어링의 개요 및 정의

AI 에이전트가 한 번 대답하고 끝나는 것이 아니라, ①작업을 계획하고 → ②코드를 짜고 → ③결과를 검증하고 → ④오류를 수정하는 '피드백 사이클(Loop)'을 스스로 반복하다가, 사람이 정해둔 '종료 조건'을 달성했을 때만 멈추도록 시스템 전체를 설계하는 기술입니다.

①
계획
Plan
→
②
코드 작성
Code
→
③
결과 검증
Verify
→
④
오류 수정
Fix
④에서 다시 ①~③으로 루프가 반복되다가, 종료 조건(예: 모든 테스트 통과)을 달성하면 멈춥니다.

비유 — 세탁기 / 건조기

매 분마다 "물 더 넣어, 10분 더 돌려"라고 지시하지 않습니다. "건조도 100%가 되면 멈춰"라고 세팅만 해두면 기계가 스스로 판단하며 돌아갑니다. 루프 엔지니어링이 바로 AI라는 건조기를 설계하는 작업입니다.

나의 역할 변화

프롬프트를 치는 '실행자(Maker)'에서, 루프를 세팅하고 최종 결과를 확인하는 '감독관(Manager)'으로 역할이 180도 바뀝니다.

Architecture

루프를 이루는 5대 핵심 부품 (+ 메모리)

단순한 챗봇을 '스스로 일하는 루프'로 진화시키려면 다음 6가지 부품이 필요합니다. 과거에는 파이썬으로 다 짜야 했지만, 현재는 Claude Code나 Codex 같은 최신 AI 툴에 모두 내장되어 있습니다.

1
자동화 (Automations) — 심장 박동매일 아침 7시, 사람이 없어도 AI가 GitHub에 접속해 어제 실패한 테스트나 새로 열린 이슈를 읽고 할 일을 스스로 발굴(Discovery)합니다.
2
워크트리 (Worktrees) — 독립된 책상AI 여러 마리를 동시에 돌리면 같은 코드를 뜯어고치다 충돌이 납니다. 각 AI에게 섞이지 않는 독립된 작업 공간(git worktree)을 내어줍니다.
3
스킬 (Skills) — 인수인계 노트AI는 세션이 켜질 때마다 백지상태입니다. SKILL.md 파일에 규칙을 한 번만 적어두면 AI가 매 작업마다 스스로 읽고 시작합니다.
4
커넥터 (Connectors/Plugins) — 손과 발Slack에 알림을 보내고, Jira 티켓 상태를 변경하고, GitHub PR을 열 수 있도록 외부 서비스와 AI를 연결하는 다리(MCP 프로토콜 등)입니다.
5
★ 서브 에이전트 (Sub-agents) — 가장 중요코드를 짜는 AI(Maker)와 검사하는 AI(Checker)를 강제로 분리합니다. AI는 자신이 짠 코드를 후하게 평가하는 편향(Self-bias)이 있어, 역할 분리가 루프의 신뢰도를 결정합니다.
6
외부 메모리 (Memory)AI의 기억력(Context)은 휘발되므로, "어디까지 했고 무엇이 남았는지"를 progress.md 같은 마크다운 파일에 지속적으로 기록하게 만듭니다.
Trade-offs

특징 및 장단점

✅ 장점

·
무인 자동화의 극치퇴근 후에도 AI가 밤새 버그를 찾고 코드를 수정하며 테스트를 돌립니다.
·
표준화된 프로세스Skills 설정을 통해 주니어 개발자가 오더라도 AI가 회사의 표준 코딩 컨벤션을 100% 강제하여 작업합니다.
·
시간 레버리지사람은 "무엇을 할 것인가"와 "최종 승인"에만 시간을 쏟으면 되므로 생산성이 기하급수적으로 늘어납니다.

❌ 단점 및 한계

·
토큰 비용 폭발AI가 자기들끼리 대화하며 무한 루프에 빠지면 하룻밤 새 수백만 원의 API 요금이 청구될 수 있습니다 (반드시 예산 상한선 설계 필요).
·
이해 부채 (Comprehension Debt)코드가 너무 빨리 만들어지면, 개발자가 자기 회사의 코드가 어떻게 돌아가는지 이해하지 못하는 사태가 벌어집니다.
·
인지적 항복 (Cognitive Surrender)AI가 가져온 결과를 귀찮아서 무비판적으로 승인(Merge)해버리면 제품의 품질이 서서히 무너집니다.
[실전]

Claude Code를 활용한 루프 엔지니어링 구축

코딩 에이전트에게 "알아서 다 고쳐줘"라고 처음부터 통째로 맡기는 것은 비용 폭발과 품질 저하를 부르는 지름길입니다. 진정한 루프 엔지니어링은 점진적 도입(L1 → L2 → L3)과 역할의 완벽한 분리(Maker vs Checker)를 통해 통제 가능한 자율 시스템을 만드는 것입니다.

리스크를 줄이는 점진적 도입 전략

단계내용승인/개입
L1 · Report-onlyAI가 문제를 발견하고 정리해서 보고만 함. 자동 수정 없음사람이 행동 패턴을 관찰
L2 · Assisted fixesAI가 수정안을 제안하고 코드를 작성적용 전 반드시 사람의 승인
L3 · Unattended안전성이 검증된 허용 목록(Allow-list) 작업만야간 무인 자동 진행

Step 1 · 스킬(Skill)부터 이식하기

AI가 세션이 바뀔 때마다 프로젝트 룰을 까먹지 않도록, 자주 하는 작업을 .claude/skills/에 SKILL.md 파일로 박아 넣습니다.

.claude/skills/daily-triage/SKILL.md
# Daily Triage Skill

## 목적
매일 아침 저장소 상태를 점검하고 처리할 일을 추린다.

## 작업 순서
1. 어제 이후의 CI 실패 로그를 읽는다.
2. 열린 이슈 중 `bug` 라벨을 확인한다.
3. 최근 24시간 커밋을 훑는다.
4. 처리할 가치가 있는 항목을 `progress.md`에 기록한다.

## 출력 형식
## [날짜] triage
- [ ] 항목 (우선순위: high/mid/low)
- 근거: [이유 작성]

## 절대 규칙
- 확신이 없는 항목은 반드시 "확인 필요"로 표시할 것.
- 이미 `progress.md`에 존재하는 항목은 중복해서 기록하지 않는다.

Step 2 · 상태 파일(Memory) 만들기

에이전트는 실행이 끝나면 모든 것을 잊어버립니다. "에이전트는 잊어도, 저장소는 잊지 않는다."

progress.md
# 진행 상황

## 완료
- [x] auth 모듈 테스트 추가 (2026-06-28)

## 진행 중
- [ ] 결제 API 타임아웃 버그 (워크트리: fix-payment-timeout)

## 대기
- [ ] 로그 레벨 설정 리팩터

Step 3 · 서브에이전트 분리하기 ★핵심★

자기가 짠 코드를 자기가 채점하면 무조건 후하게 점수(Self-bias)를 줍니다. .claude/agents/에 평가자 에이전트를 정의합니다.

.claude/agents/reviewer.md
# Reviewer Agent

## 역할
다른 에이전트가 작성한 코드를 비판적으로 검토한다. **너는 절대 코드를 직접 쓰지 않는다.**

## 검토 기준
1. 프로젝트 스킬(SKILL.md)의 코딩 컨벤션 준수 여부
2. 기존 테스트 코드의 통과 여부
3. 엣지 케이스(Edge case) 처리 여부
4. 보안 취약점 (입력값 검증, 시크릿 키 노출 등)

## 출력 형식
- 통과/실패 판정 명시
- 실패 시: 구체적인 수정 요구사항을 작성하여 작성자(Maker) 에이전트에게 반환할 것.

Step 4 · 오토메이션으로 부품 묶기 (/loop & /goal)

조립된 부품들을 Claude Code의 내장 명령어로 실행합니다. 도입 단계(L1 → L2)에 따라 명령어가 다릅니다.

L1 — 관찰 및 보고만
# 매일(1d) 스킬을 실행하고 마크다운에 기록만 하도록 지시
/loop 1d "daily-triage 스킬을 실행하고 progress.md에 기록만 해줘. 절대 코드를 수정하지 마."

며칠 관찰 후 AI의 분류가 정확하다면, /goal 명령어로 종료 조건(Stop Condition)이 달성될 때까지 무한 반복하는 진짜 루프를 가동합니다.

L2 — 수정 및 검증 루프 가동
/goal "progress.md의 'high' 우선순위 항목에 대해 격리된 워크트리(worktree)를 열고 수정안을 작성해.
그 후 reviewer 에이전트에게 검토를 받고, 통과하면 PR(Pull Request)을 열어줘.
단, Merge는 절대 하지 마.
[종료 조건]: 모든 테스트 코드가 통과하고 lint 에러가 0이 되면 완료된 것으로 간주하고 멈춰."
💡 실무 핵심 포인트 — /goal 명령어의 가장 중요한 점은 '기계가 판별할 수 있는 명확한 종료 조건(예: 테스트 통과, 린트 클린)'을 주는 것입니다. "코드가 좋아 보이면 멈춰"라고 지시하면 검사 모델이 판단하지 못해 토큰(비용)만 태우며 무한 루프에 빠지게 됩니다.

생산성을 극대화하는 오픈소스 CLI 도구

매 프로젝트마다 처음부터 세팅하는 건 비효율적입니다. cobusgreyling/loop-engineering 공개 저장소의 CLI 도구로 구축 속도를 높일 수 있습니다.

loop-engineering-cli.sh
# ① 스타터 스캐폴딩 — 루프 뼈대 자동 생성
npx @cobusgreyling/loop-init . --pattern daily-triage --tool claude

# ② 토큰 비용 추정기 — 비용 폭탄 방지
npx @cobusgreyling/loop-cost --pattern daily-triage --level L1

# ③ 루프 준비도 오딧(Audit) 점검
npx @cobusgreyling/loop-audit . --suggest
마무리 요약 — 실전에서 Claude Code로 루프를 짤 때는 1) SKILL.md로 컨텍스트를 고정하고, 2) progress.md로 기억을 외부에 저장하며, 3) reviewer.md를 통해 검증자를 철저히 분리하는 것이 핵심입니다. 여기에 /goal 명령어로 명확한 종료 조건을 걸어두면, 자는 동안에도 AI가 안전하게 버그를 고치고 PR을 올려두는 완벽한 자율 시스템이 완성됩니다.

Conclusion

마치며 — '시작 버튼'만 누르는 사람이 되지 마세요

루프 엔지니어링은 우리에게 엄청난 자유를 줍니다. 하지만 구글의 Addy Osmani는 다음과 같은 뼈 있는 경고를 남겼습니다.

"루프를 설계하십시오. 단, 그저 '시작(Go)' 버튼만 누르는 구경꾼이 아니라, 끝까지 코드의 품질을 책임지는 '진짜 엔지니어'로 남을 작정으로 설계하십시오."

루프는 우리를 타이핑의 고통에서 해방시켜 주지만, "이 코드가 우리 서비스에 올라가도 안전한가?"를 최종적으로 검토하고 승인하는 것은 영원히 인간의 몫입니다.

기억할 것 한 줄 — AI가 스스로 일감을 찾고 고치는 이 강력한 시스템을 업무에 도입해보세요. 단, 첫 시작은 거창한 자동화가 아니라 귀찮은 에러 로그를 요약해주는 작은 스킬(SKILL.md) 한 장부터 시작하는 것을 추천합니다 🚀
