토큰 최적화와 비용 절감

똑같은 작업을 시켜도 왜 비용이 다를까요?[cite: 6] 에이전트 도구의 토큰 비용 산정 원리부터 프롬프트 캐싱, 컨텍스트 다이어트, 서브 에이전트를 활용한 스마트한 사용법까지 완벽하게 정리합니다.[cite: 6]

프롬프트 캐싱 컨텍스트 다이어트 서브 에이전트
01 · Pricing Factors

토큰 단가를 결정하는 3가지 요소

AI 요금은 토큰 단위로 부과되지만, 실제 비용은 GPU가 모델을 돌리는 '추론 시간'입니다.[cite: 6] 토큰 처리 시간과 가격을 결정하는 핵심 요소는 다음과 같습니다.

01 · 모델 (Model)

파라미터 크기에 비례합니다.[cite: 6] 같은 토큰이라도 거대 모델은 훨씬 많은 연산이 필요하므로 비용이 높습니다.[cite: 6] 단순 작업엔 작은 모델을 써야 합니다.[cite: 6]

02 · 입출력 방향 (I/O)

입력(프리필)보다 출력(디코드) 토큰이 약 5배 비쌉니다.[cite: 6] 출력은 다음 토큰을 순차적으로 만들어야 하므로 GPU를 더 오래 점유하기 때문입니다.[cite: 6]

03 · 캐시 (Cache)

동일한 앞부분 컨텍스트를 재사용하면 전가의 10분의 1(0.1배) 가격으로 처리할 수 있습니다.[cite: 6] 할인을 날리지 않도록 관리하는 것이 핵심입니다.[cite: 6]

"우리가 화면에서 보는 답변은 출력 토큰의 일부일 뿐, 상당 부분은 모델이 속으로 하는 사고(Thinking) 토큰입니다.[cite: 6] Effort 설정을 높이면 보이지 않는 출력 토큰이 늘어나 5배 단가로 과금됩니다.[cite: 6]"

02 · Prompt Caching

프롬프트 캐싱의 원리

직전 요청과 똑같은 앞부분 대화를 메모리에 보관하여 재사용함으로써 엄청난 비용 절감을 가져옵니다.[cite: 6]

캐싱이 없을 때 (정가 1.0)
1회차 전송 (정가)[cite: 6]1.0
나머지 19회 전송 (정가)[cite: 6]19.0
총 비용 추정치[cite: 6]20.0
캐싱 활용 시 (최대 5배 절감)[cite: 6]
1회차 저장 비용 (약 2.0배)[cite: 6]2.0
이후 19회 재사용 (0.1배 × 19)[cite: 6]1.9
총 비용 추정치[cite: 6]3.9
도미노가 무너지는 순간 (캐시가 깨지는 조건)[cite: 6]
캐시는 맨 앞칸부터 비교합니다.[cite: 6] 대화 중간에 아래 행동을 하면 꼬리표가 바뀌거나 기차 칸이 통째로 바뀌어 이후의 모든 내용이 전가로 다시 계산됩니다.[cite: 6]
  • 모델이나 Effort 설정 변경: 내용이 같아도 처리 꼬리표가 달라져 무효화됩니다.[cite: 6]
  • /compact 명령어 실행: 기존 대화를 요약본으로 갈아치우므로 과거 캐시가 통째로 날아갑니다.[cite: 6]
  • 1시간 이상 자리 비움: 캐시는 마지막 대화 이후 한 시간 뒤 서버에서 자동으로 만료되어 리셋됩니다.[cite: 6]
03 · Context Management

작업 책상(컨텍스트) 다이어트

어떤 것도 한 번만 전송되지 않습니다.[cite: 6] 세션이 유지되는 한, 읽은 파일과 도구 출력 로그는 대화마다 눈덩이처럼 누적 전송됩니다.[cite: 6]

비용을 낭비하는 짐(Bloat)[cite: 6]

  • 연결해 두고 쓰지 않는 방대한 MCP 서버[cite: 6]
  • "뭔가 잘 안 돼"처럼 모호하게 지시하여 클로드가 불필요하게 뒤져본 수많은 파일들[cite: 6]
  • 명령어 실행 시 화면을 채우는 길고 긴 에러 로그들[cite: 6]

컨텍스트 최적화 전략[cite: 6]

  • 쓰지 않는 MCP 연결 해제하기[cite: 6]
  • @파일명으로 맨션하여 파일 검색 과정을 생략 (파일은 한 번만 멘션하기)[cite: 6]
  • 전혀 다른 새로운 작업 시작 시 /clear 로 백지화[cite: 6]
흐름 복구를 위한 명령어 선택 가이드[cite: 6]
/rewind
최근 대화 몇 개만 엉뚱하게 엇나갔을 때[cite: 6]
뒤에 붙은 불량 칸만 떼어냅니다.[cite: 6] 앞부분의 캐시는 완벽하게 유지됩니다.[cite: 6]
/compact
대화가 너무 길어져 다이어트가 필요할 때[cite: 6]
지나간 과정을 요약본으로 압축합니다.[cite: 6] 단, 캐시가 초기화되며 생성 비용이 듭니다.[cite: 6] (자리를 1시간 이상 비우기 직전에 미리 해두는 것이 이득입니다.[cite: 6])
04 · Sub-Agents

서브 에이전트 활용법

짐이 생길 작업을 처음부터 다른 곳(격리된 공간)에서 시키는 방법입니다.[cite: 6]

메인 클로드 (팀장) ↔ 서브 에이전트 (직원)[cite: 6]

"이 수천 줄짜리 로그에서 에러 원인을 찾아줘"라고 메인에서 시키면, 로그 수천 줄이 메인 세션 끝까지 짐으로 남습니다.[cite: 6]

하지만 "이 파일은 서브 에이전트로 검토해 줘"라고 지시하면, 서브 에이전트가 백지 상태에서 로그를 뒤져보고, 메인 대화로는 "원인은 이것"이라는 단 한 줄의 최종 답변만 들고 복귀합니다.[cite: 6] 탐색 과정에서 소모된 데이터 찌꺼기들은 서브 에이전트가 사라질 때 함께 폐기되어 메인 컨텍스트를 깨끗하게 유지합니다.[cite: 6]

서브 에이전트의 단점독립적으로 시작하므로 메인의 과거 대화 맥락을 전혀 모릅니다.[cite: 6] 파일도 처음부터 다시 읽어야 하므로, 아주 단순하고 작은 작업에 쓰면 오히려 추가 비용(손해)이 발생합니다.[cite: 6]
적합한 작업'읽어야 할 분량은 산더미인데, 이후 대화에 보관할 가치가 없는 검색/분석 작업'에 최적화되어 있습니다.[cite: 6]
05 · Summary

비용에 악영향을 미치는 요인 TOP 4

엔트로픽이 공식 블로그에서 밝힌 비용 낭비의 핵심 원인들을 영향도가 큰 순서대로 정리했습니다.[cite: 6]

01긴 세션 유지 — 한 세션에서 대화 전체가 반복 전송되므로 가장 큰 토큰 낭비를 유발합니다.[cite: 6] /clear 와 /compact로 세션을 짧고 가볍게 유지하세요.[cite: 6]
02컨텍스트 과부하 — 쓰지 않는 도구(MCP)나 불필요하게 엮인 파일 로그들이 매번 다시 전송됩니다.[cite: 6] @파일명 멘션과 서브 에이전트로 짐을 덜어내세요.[cite: 6]
03과도한 모델과 Effort 설정 — 1, 2번에서 발생한 방대한 양에 비싼 단가가 곱해집니다.[cite: 6] 새 세션을 열 때는 반드시 의도에 맞게 설정을 점검하세요.[cite: 6]
04캐시 초기화 (도미노 붕괴) — 세션 중간에 설정을 바꾸거나 한 시간 이상 자리를 비우면 저장된 캐시가 날아가 모든 걸 정가로 다시 계산해야 합니다.[cite: 6]
