코드는 더 이상
병목이 아니다

Claude Code 같은 에이전트 코딩 도구 덕분에 구현 속도는 이미 달라졌지만, 그 주변의 승인·리뷰·인수인계 프로세스는 그대로였습니다. Anthropic Applied AI 팀이 정리한 이 플레이북은 전통적인 선형 SDLC를, 매 지점에 AI가 결합된 비선형 루프로 다시 그립니다. Plan → Design → Build → Test → Deploy → Maintain 6단계와 그 사이를 잇는 커밋 아티팩트 체인을 정리했습니다.

00 · Why Now

코드가 병목에서 풀리면 무슨 일이 벌어지는가

빌드 단계가 시간 단위로 압축되는 순간, 세 가지가 사실이 됩니다. 이 압력이 SDLC 전체를 다시 설계해야 하는 이유입니다.

⚖️ 병목의 이동

  • 병목이 Plan·Review/Test·Deploy처럼 여전히 사람 속도로 도는 단계로 옮겨감

🧩 통제와 현실의 괴리

  • 한 줄씩 손으로 리뷰하던 방식은 에이전트가 diff 대부분을 쓰는 순간 유지 불가능해짐

💰 거버넌스 비용 증가

  • 예외 처리가 여전히 주간·월간 회의를 거치면 비용만 커짐
AI-네이티브 SDLC란 — 기존의 통제 목표는 유지하되 새로운 방식으로 강제하는, 다시 설계된 프로세스입니다. 선형 흐름 대신 루프가 되고, 각 단계 끝에 커밋되는 아티팩트가 다음 단계를 자동으로 트리거합니다.
The Shift

6단계에 걸친 변화 — 전통 SDLC vs AI-네이티브 SDLC

단계 전통 SDLC AI-네이티브 SDLC
Plan위원회가 요구사항을 수집, 워크숍·승인을 거쳐 손으로 정리Claude가 원천에서 곧바로 intent.md로 종합 — 사람이 읽고 기계가 실행 가능
Design분석가가 스펙을 쓰고 디자이너가 그것을 다시 해석요구사항+설계가 한 세션으로 압축, 스킬로 인코딩된 표준이 안내, git으로 버전 관리
Build테스트·코드를 손으로 작성, 문서는 개발 후 별도 작성AI가 테스트·코드 생성, 지식은 버전 관리되는 CLAUDE.md·스킬로 유지
Test단계 경계마다 QA 게이트구현 전체에 걸쳐 짜여진 지속적 평가(evals)
Deploy모든 줄을 사람이 리뷰, 거버넌스는 불규칙한 리뷰 사이클에이전트 리뷰 다층화 + 규제·중요 코드만 사람 리뷰, 훅이 승인 게이트 역할
Maintain사람이 프로덕션의 버그를 지켜봄에이전트가 실시간 모니터링, 통제 밴드 이탈 시 새 intent.md로 루프 재진입
공통 스레드 — 커밋되는 아티팩트입니다. intent.md → spec.md → plan.md → diff → 리뷰 결과 → incident record가 이어지며, 각 단계는 커밋으로 끝나고 다음 단계는 그 커밋을 읽는 것으로 시작합니다. 이 커밋 체인 자체가 감사 추적(audit trail)이 됩니다.
The Loop

6단계 논스톱 루프

각 플레이(play)는 무엇이 바뀌는지, 시작하는 법, 구체적 실행 단계, 거버넌스 고려사항, 성과 측정법을 다룹니다.

1
Plan

아이디어를 intent.md로 한 번에 포착 — 원발안자의 언어 그대로.

intent.md
2
Design

요구사항+설계를 한 세션에서, 스킬로 인코딩된 정책을 적용하며 압축.

spec.md
3
Build

Plan Mode로 승인된 계획 없이는 구현하지 않음. 지식은 CLAUDE.md·스킬로.

plan.md + diff
4
Test

사람이 보기 전에 스스로 검증. 지속적 평가가 설정 변경까지 회귀 테스트.

test 결과
5
Deploy

양방향 리뷰 + 훅 기반 승인 게이트. 에이전트는 프로덕션 게이트 앞까지만.

PR + 리뷰 결과
6
Maintain

통제 밴드 이탈 시 사람 개입 없이 진단, 새 intent.md로 루프 재진입.

incident record
Stage 01 · Plan

아이디어가 사람을 기다리지 않는다

Capture as intent.md

아이디어가 생기면 원발안자가 Claude와 브레인스토밍하며 proto-spec을 만듭니다. Claude는 애널리스트가 물을 법한 질문(범위·사용자·제약·성공 기준)을 던지고, 결과를 조직의 템플릿에 맞춰 intent.md로 작성합니다. 제품 오너가 검토·수정한 뒤 커밋하면 다음 단계가 시작됩니다.

📊 선행지표: 첫 대화→커밋까지 시간 📊 후행지표: Design 단계 진입 승인율(survival rate)
# Intent: claims status self-service
Author: J. Ortiz (claims operations). Status: draft.

## Problem
Customers phone the contact center to ask where their claim is.

## Proposed outcome
Customers see claim status, next step and expected date in the portal.
Stage 02 · Design

요구사항과 설계가 한 세션으로 압축된다

Requirements and Design

승인된 intent.md를 받은 Claude가 브랜드·보안·컴플라이언스·UX 스킬의 안내를 받아 요구사항+설계 스펙을 만듭니다. 제품 오너는 쓰지 않고 검토만 합니다. 프론트엔드 작업은 Claude Design으로 목업까지 만든 뒤 Claude Code로 넘겨 빌드합니다.

📊 선행지표: intent.md→spec.md 소요 시간 📊 후행지표: plan.md 이후 발생한 요구사항 재작업
Stage 03 · Build

승인된 계획 없이는 아무것도 구현하지 않는다

Plan Mode 기본값
엔지니어가 Plan Mode에서 세션을 시작해 spec.md를 주고 Claude가 파일 목록·작업 순서·테스트까지 담긴 계획을 세우게 합니다. 승인된 계획은 plan.md로 커밋되어 이후 단계의 대조 기준이 됩니다.
CLAUDE.md
새 합류자가 첫날 알아야 할 컨벤션·명령어·아키텍처·자주 하는 실수를 담은 파일. /init으로 생성하고, 실수를 두 번 하면 그 교정을 파일에 추가합니다. 한 페이지 이내로 유지합니다.
Skills (제도적 지식)
보안 표준·API 컨벤션·브랜드 규칙처럼 일관되게 적용돼야 하는 지식을 스킬로 인코딩합니다. 스킬은 권고적 통제이며, 예외 없이 지켜져야 하는 정책은 훅으로 뒷받침합니다.
Hooks (빌드타임 가드레일)
보호된 경로 편집 차단, 편집 후 자동 포맷·린트 실행, 자격증명이 diff에 들어가지 않게 막는 등 결정론적 계층입니다.
병렬 세션 & 서브에이전트
한 엔지니어가 git worktree로 여러 세션을 동시에 굴리고, 반복되는 검증·탐색 작업은 서브에이전트(예: verifier)로 분리합니다. 시작은 세션 2~3개가 적당합니다.
Auto 모드로 — CLAUDE.md·스킬·훅·테스트 스위트라는 가드레일이 성숙할수록, 좁은 반경의 정형화된 작업에서는 Auto-accept가 기본값이 됩니다. 감독의 방식이 "편집을 하나하나 지켜보는 것"에서 "긴 자율 세션 뒤 아티팩트를 검토하는 것"으로 옮겨갑니다.
Stage 04 · Test

사람이 보기 전에 스스로 검증한다

피드백 루프 + 지속적 평가(Continuous Evals)

테스트·빌드·스크린샷 비교처럼 자기 작업을 확인할 방법을 세션에 항상 쥐여줍니다. 버그 수정은 실패하는 테스트를 먼저 작성해 커밋하고, 그 테스트를 건드리지 않은 채 통과시키는 방식으로 진행합니다. 한편 지속적 평가는 CLAUDE.md·스킬·훅이 바뀔 때마다 CI에서 도는 회귀 스위트로, 에이전트를 조종하는 설정 자체를 코드처럼 테스트합니다.

📊 선행지표: 에이전트 변경의 1차 CI 통과율 📊 후행지표: PR당 리뷰 시간, 변경 실패율
Stage 05 · Deploy

리뷰는 양방향으로, 거버넌스는 에이전트가 행동하는 순간 강제된다

PR 리뷰 루프
Claude가 들어오는 PR을 조직의 정책(REVIEW.md)에 따라 리뷰하고, 자기 PR의 리뷰 코멘트에도 직접 대응합니다. 사람의 관심은 의도와 위험 판단으로 이동합니다.
훅 = 승인 게이트
빌드 단계의 훅이 허용/차단이었다면, 배포 단계의 훅은 특정 인물의 승인이 있을 때까지 멈추는 방식으로 릴리스 게이팅을 수행합니다.
CI/CD 통합
Claude가 파이프라인 안에서 비대화형으로 실행되어 빌드 실패 원인 진단, 변경 로그 초안, 배포·롤백까지 MCP를 통해 수행하되, 프로덕션 자격증명은 기본적으로 보유하지 않습니다.
지배 원칙 — 에이전트는 프로덕션 게이트까지는 행동할 수 있지만, 그 문턱을 넘지 못합니다. 브랜치 보호로 모든 쓰기는 PR을 거치고, 프로덕션 배포 훅은 지정된 릴리스 매니저의 승인을 요구합니다.
Stage 06 · Maintain

루프가 닫힌다 — 사람 없이 트리거되고, 사람이 판단으로 돌아온다

Closing the Loop

결정론적 스크립트가 프로덕션을 감시하다가 통제 밴드 이탈(예: CI 테스트 실패율 3σ 초과)을 감지하면, 개입 없이 Claude를 호출합니다. Claude는 진단 결과를 Stage 1 형식의 intent.md로 작성하고, 이 아티팩트가 다시 파이프라인 전체를 통과합니다. 사람은 큐를 트리아지할 뿐, 시작할 필요가 없습니다.

🔍 Claude Security — 예약된 코드베이스 취약점 스캔 💬 Claude Tag — Slack에서 인시던트 최초 대응
예시 — 배포 후 5xx 비율이 3σ를 넘고 최근 배포가 있었다면, 에이전트가 기존 롤백 파이프라인을 직접 트리거합니다. 탐지는 항상 결정론적이며, 밴드가 무엇을 할 수 있는지 결정합니다.
Closing Thoughts

마치며

이 플레이북은 "사람의 판단은 그대로 중심에 두면서, 루프는 계속 돈다"는 원칙을 축으로 합니다. 모델과 하네스가 발전할수록, 조직은 코드를 만드는 방식뿐 아니라 SDLC 전체를 바꿀 수 있습니다.

01intent.md → spec.md → plan.md → diff → 리뷰 결과 → incident record로 이어지는 커밋 아티팩트 체인이 곧 감사 추적입니다.
02Build 단계는 Plan Mode·CLAUDE.md·Skills·Hooks·서브에이전트로, Deploy는 양방향 리뷰와 훅 게이트로 뒷받침됩니다.
03Maintain에서 루프는 사람 없이 트리거되고 진단되며, 결과는 다시 intent.md로 Plan 단계에 진입해 루프가 이어집니다.
다음 단계 — 팀의 SDLC에서 가장 반복적이고 병목이 큰 단계 하나를 골라, 해당 플레이의 "Getting started" 섹션대로 인프라를 먼저 세팅해보세요. 6단계를 한 번에 바꿀 필요는 없습니다.
