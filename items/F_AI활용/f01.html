01

지식이 휘발되는 문제

// 대화창이 닫히는 순간 사라지는 AI의 답

매일 ChatGPT나 Claude에 PDF 논문이나 코드를 올리고 질문합니다. 하지만 며칠 뒤 비슷한 질문을 하려면, 똑같은 문서를 다시 올리고 팀 상황을 다시 설명해야 합니다.

훌륭한 답도 대화창이 닫히면 허공으로 사라진다.

이 '지식 휘발' 문제에 답답함을 느낀 전 OpenAI 공동창업자 안드레 카파시는 2026년 4월 GitHub Gist에 폴더 3개짜리 아이디어를 올렸고, 순식간에 1,600만 뷰를 기록하며 개발자 커뮤니티를 뒤집어 놓았습니다. 그것이 'LLM Wiki'입니다.

02

LLM Wiki란 무엇인가

// 검색이 아니라, 한 번 컴파일해 두는 지식베이스

LLM이 직접 읽고, 요약하고, 상호 연결하며 지속해서 유지보수하는 마크다운 기반의 개인·팀 지식 베이스 구축 패턴이다. 특정 앱이 아니라, 로컬 폴더와 AI 에이전트만 있으면 누구나 만드는 '운영 방식'이다.

RAG · 인터프리터

매번 해석

질문이 들어올 때마다 원본 문서에서 조각을 검색해, 그때그때 답변을 조립한다. 코드를 한 줄씩 해석하는 인터프리터에 가깝다.

LLM WIKI · 컴파일러

한 번 컴파일

원본이 들어오는 순간 위키 페이지로 '컴파일'해 둔다. 이후엔 원본을 뒤지지 않고 정리된 위키를 읽어 즉시 답한다.

지식이 파편화되지 않고, 시간이 지날수록 눈덩이처럼 축적(Accumulation)되는 구조다.
03

3계층 아키텍처

// 폴더 2개 + 파일 1개, 놀라울 만큼 단순한 구조

raw/진실의 원천 · 불변

Raw Sources

수집한 PDF 논문, 회의 메모, 웹 기사, 이미지 등 원본이 저장되는 곳.

절대 수정·삭제하지 않는 읽기 전용. 위키가 틀렸을 때 팩트 체크의 기준이 된다.

wiki/LLM이 컴파일한 지식층

Wiki

LLM이 raw/의 자료를 읽고 요약해 만든 마크다운(.md) 페이지들이 모이는 곳.

인물·개념·종합으로 나뉘고, 페이지 간 [[백링크]]로 거대한 지식 그래프를 이룬다. 쓰기·수정은 LLM이 맡는다.

CLAUDE.md운영 규칙서 · 핵심

Schema

"어떤 형식으로 쓰고, 내용이 충돌하면 어떻게 표시하라"를 알려주는 지시문.

이게 없으면 위키는 제멋대로 쓰여 난장판이 된다. LLM을 '규율 잡힌 사서'로 만드는 파일.

04

3대 운영 작업

// 이 세 작업으로 위키 생태계가 살아 숨 쉰다

INGEST

흡수·통합

raw/에 새 PDF를 넣고 명령하면 AI가 읽어 기존 wiki/ 페이지를 갱신하거나 새로 만든다. index.md·log.md도 함께 갱신된다.

QUERY

질의·확장

정리된 위키에 질문하면 AI가 index.md로 관련 페이지를 찾아 답한다. 가치 있는 답변은 새 페이지로 영구 보존된다.

LINT

건강 점검

주 1회쯤 전체 점검을 명령한다. AI가 모순되는 주장, 고립된 페이지(Orphan), 오래된 정보를 찾아 수정을 제안한다.

05

특징 및 장단점

// 복리로 쌓이는 대신, 관리가 필요하다

▲ 장점

복리 효과 (점진적 축적)휘발되는 RAG와 달리, 시간이 지날수록 내 입맛에 맞게 고도화된 나만의 백과사전이 만들어진다.
합성 질문에 강함"최근 6개월 트렌드 변화" 같은 질문도 이미 종합 페이지가 컴파일돼 있어 깊이 있게 답한다.
낮은 진입 장벽과 비용벡터 DB·임베딩 인프라가 필요 없다. 마크다운 파일만 있으면 되므로 유지 비용이 0원에 가깝다.

▼ 단점 및 한계

대규모 확장의 한계수만~수백만 건엔 부적합하다. 100~수백 개 문서, 개인·소규모 팀이 스위트스팟이다.
환각의 누적잘못 요약된 정보가 공식 지식처럼 굳는다. 사람의 검토와 raw 대조가 필수다.
프롬프트 인젝션 위협외부 문서에 숨은 악성 명령이 있으면, AI가 정리 중 오작동할 수 있다.
06

주요 활용 분야

// 코드베이스 · 연구 · 기획, 어디든

¶

개인 연구 · 장기 학습 (PKM)

수개월에 걸쳐 읽은 논문·기사·아이디어 메모를 주제별로 엮어, 점진적으로 발전하는 논문 초안을 구축한다.

✦

여행 · 프로젝트 기획

흩어진 블록·예약·예산·동반자 정보를 넣으면 AI가 '숙소 비교', '일정표', '주의사항'으로 정리해 준다.

07

실전 구축 — 10분 만에

// Obsidian(에디터) + Claude Code(터미널 에이전트)

폴더 구조 세팅

터미널을 열고 옵시디언 볼트(Vault)로 쓸 디렉토리를 만든다.

mkdir my-llm-wiki && cd my-llm-wiki
mkdir -p raw/papers raw/articles
mkdir -p wiki/entities wiki/concepts wiki/synthesis
touch CLAUDE.md index.md log.md

스키마(CLAUDE.md) 작성

AI가 지켜야 할 룰을 정한다. CLAUDE.md를 열고 아래를 붙여넣는다.

# Wiki 운영 규칙

## 절대 규칙
- `raw/` 파일은 절대 수정·삭제 금지 (읽기 전용)
- 불확실한 내용은 단정하지 말고 `[확인 필요]` 표시
- 모든 페이지 하단에 `raw/` 출처 명시

## Ingest 워크플로우
1. `raw/`의 새 자료를 읽고 핵심 파악
2. 관련 페이지가 있으면 덧붙여 업데이트 (신규 생성보다 우선)
3. 관련 페이지끼리 `[[페이지 이름]]` 백링크 연결
4. 끝나면 `index.md`와 `log.md` 갱신

원본 자료 넣고 Ingest 실행

  1. raw/papers/에 읽고 싶던 PDF·텍스트 2~3개를 복사해 넣는다.
  2. claude를 실행해 에이전트를 켠다 (npm i -g @anthropic-ai/claude-code로 사전 설치).
  3. 프롬프트에 아래처럼 명령한다.
"CLAUDE.md 규칙을 읽고, raw/의 새 자료를 ingest해서 wiki/에 마크다운으로 정리해 줘."

결과 확인 및 질문 (Query)

옵시디언을 열면 wiki/ 아래 요약 페이지들이 [[ ]]로 링크된 채 생성돼 있다. 이제 다시 질문한다.

"index.md를 먼저 읽고, 정리된 위키로 'LLM 아키텍처 한계점'을 종합해 synthesis에 새 페이지로 저장해 줘."

09

마치며

// 검색이 아니라, 기억을 유지보수하라

인류는 모든 걸 머릿속에 기억하려 했고, 인터넷 이후엔 검색창에 의존했으며, AI 직후엔 RAG로 매번 문서를 던졌습니다.

카파시의 LLM Wiki는 새로운 깨달음을 줍니다 — 가장 중요한 것은 매번 검색하는 것이 아니라, 잘 정돈된 '기억(Memory)'을 꾸준히 유지보수하는 것이라는 사실. 복잡한 벡터 DB나 비싼 클라우드 서버는 필요 없습니다.

빈 폴더 3개와 옵시디언, AI 에이전트로 오늘 1주일짜리 파일럿을 시작해 보라.
